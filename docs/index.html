Overview / 总览

用数据说话 By the Numbers

MathMod-Pilot 将数学建模竞赛的完整工作流封装为 15 个可插拔技能，通过 8 阶段流水线串联，采用自主研发的 Generate-Verify-Revise 迭代架构确保计算结果的可靠性。 MathMod-Pilot encapsulates the complete mathematical modelling competition workflow into 15 pluggable skills, connected through an 8-stage pipeline, powered by the independently developed Generate-Verify-Revise iterative architecture to ensure computational reliability.

Architecture / 系统架构

动态插件架构 Dynamic Plugin Architecture

核心 Agent 不硬编码任何技能。它在导入时扫描 src/mathmod_pilot/skills/ 目录，动态发现并注册每个技能文件夹中的 BaseSkill 子类。添加新技能只需放入一个文件夹——零配置扩展。 The core agent does not hard-code any skill. It scans src/mathmod_pilot/skills/ at import time, dynamically discovering and registering the BaseSkill subclass in each skill folder. Adding a new skill requires only dropping in a folder—zero configuration.

🧩

BaseSkill 抽象基类 BaseSkill ABC

每个技能必须实现 execute(self, inputs: dict) -> dict 抽象方法。基类自动解析 SKILL.md 的 YAML front-matter，填充 SkillMeta 数据类（名称、描述、版本、阶段、层级）。 Every skill must implement execute(self, inputs: dict) -> dict. The base class auto-parses the YAML front-matter from SKILL.md to populate a SkillMeta dataclass (name, description, version, stage, tier).

🔍

discover_skills() 动态扫描 discover_skills() Scanner

遍历 skills/ 下每个包含 SKILL.md 的子目录。若存在 skill.py，则导入并实例化首个 BaseSkill 子类；若无 skill.py，则回退到 PromptSkill 包装器，使纯 Markdown 技能也可调用。 Iterates every sub-directory of skills/ that contains a SKILL.md. If skill.py exists, it imports and instantiates the first BaseSkill subclass; otherwise it falls back to a PromptSkill wrapper so that pure-markdown skills remain callable.

🤖

MathModPilotAgent 控制器 MathModPilotAgent Controller

持有技能注册表，提供两种执行模式：run_skill(name, inputs) 调用单个技能；run_pipeline(inputs, stages) 串联 S0→S7，将上下文字典逐级传递，使每个阶段获得前一阶段的输出。 Holds the skill registry and provides two execution modes: run_skill(name, inputs) invokes a single skill; run_pipeline(inputs, stages) chains S0→S7, threading the context dictionary forward so each stage receives the previous stage's output.

📦

优雅降级机制 Graceful Degradation

仅 PyYAML 为硬依赖。所有科学计算库（numpy、scipy、scikit-learn、matplotlib 等）均为可选 extras，技能在后端缺失时自动降级而非崩溃。 Only PyYAML is a hard dependency. All scientific libraries (numpy, scipy, scikit-learn, matplotlib, etc.) are optional extras; skills degrade gracefully when their backends are absent.

🔗

Pipeline 上下文传递 Pipeline Context Threading

S1 的硬断言、等X约束、方法路由决策自动传递给 S3；S3 的求解结果传递给 S4 做灵敏度分析；S4 的验证报告传递给 S5 生成验证类图表；S5 的图表传递给 S6 写入论文——全链路数据自动流转。 S1's hard assertions, equal-X constraints, and method routing decisions flow to S3; S3's results flow to S4 for sensitivity analysis; S4's validation report flows to S5 for verification charts; S5's figures flow to S6 for paper writing—full-chain automatic data flow.

🛡️

三层规则优先级体系 Three-Tier Rule Priority

L1 全局硬约束（必须遵守）→ L2 条件硬约束（带 Gate 检查，如 v8 光学规则仅对 A 题生效）→ L3 软建议（可灵活调整）。所有技能共享此体系，受学习机制 v3.0 守护。 L1 global hard constraints (mandatory) → L2 conditional hard constraints (with Gate checks, e.g. v8 optics rules apply only to Problem A) → L3 soft suggestions (flexible). All skills share this system, guarded by learning mechanism v3.0.

Pipeline / 流水线

S0 → S7 八阶段流水线 S0 → S7 Eight-Stage Pipeline

从需求构思到论文终审，每个阶段由一个核心技能驱动，上下文字典在阶段间自动传递，形成完整的建模竞赛工作流闭环。 From requirement brainstorming to paper final review, each stage is driven by a core skill, with the context dictionary automatically threaded between stages, forming a complete modelling competition workflow loop.

Core Mechanism / 核心机制

Generate-Verify-Revise 迭代架构 Generate-Verify-Revise Iterative Architecture

mle-solver（S3）的核心机制。代码生成后必须在本地执行并验证通过——无 Traceback、硬断言全通过、物理合理性检查通过、交叉验证通过——任一未通过必须进入 Debug 回路修正，直至全部通过或达到最大修正次数。 The core mechanism of mle-solver (S3). Generated code must be executed locally and pass verification—no Traceback, all hard assertions pass, physical feasibility check passes, cross-validation passes—any failure triggers the Debug loop for revision, until all pass or the maximum revision count is reached.

HARD-GATE 硬门禁：HARD-GATE: 代码生成后必须在本地执行并验证通过。任一检查未通过，禁止返回"成功"结果，必须进入 Debug 回路。这一机制杜绝了"看似正确但实际有误"的模型代码被带入后续阶段。 Generated code must be executed locally and pass verification. If any check fails, returning a "success" result is forbidden—the Debug loop must be entered. This mechanism prevents "looks-correct-but-actually-wrong" model code from being carried into subsequent stages.
